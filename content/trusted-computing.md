# Trusted Computing: Secure Boot, TPM & IMA

> **Goal:** understand the chain of trust from firmware to kernel to userspace — how the platform verifies what it boots, measures it into tamper-proof hardware, and uses those measurements to enforce runtime integrity. This is the plumbing beneath "trusted execution" and "confidential computing."

## The mental model

Every computing platform has a moment of faith: the first instruction executed after power-on must be trusted. There is no verification before that moment — the CPU can't verify the firmware image because the CPU hasn't yet loaded the verification code.

The solution is **chains of trust**:

```
Hardware Root of Trust (immutable ROM, fused keys)
    ↓ verifies signature of
  Platform Firmware (UEFI)
    ↓ verifies signature of
  Bootloader (shim + GRUB)
    ↓ verifies signature of
  Linux Kernel
    ↓ verifies signature of
  Kernel Modules
    ↓ measures and enforces integrity of
  Userspace binaries, configuration, containers
```

Each link in the chain verifies the next link's cryptographic signature before passing control. But verification alone isn't enough — we also need **attestation**: proof to a third party that a specific platform booted a specific chain. That's where the TPM comes in.

## Secure Boot: the first link

UEFI Secure Boot (`CONFIG_EFI_STUB`) is the mechanism that prevents unauthorized code from running at boot. The UEFI firmware contains a database of trusted signing keys:

```bash
# UEFI Secure Boot variables (accessible from Linux via efivarfs)
ls /sys/firmware/efi/efivars/
# db  = authorized signature database (keys and hashes)
# dbx = forbidden signature database (blacklisted keys/hashes)
# KEK = Key Exchange Keys (authorize updates to db/dbx)
# PK  = Platform Key (one key, controls KEK updates)
```

The chain:
1. **PK** (OEM-controlled) signs the **KEK**
2. **KEK** (OEM + Microsoft) signs the **db/dbx**
3. **db** contains hashes and certificates of bootloaders allowed to execute
4. Firmware checks the bootloader's signature against **db** before executing it

```bash
# Is Secure Boot active?
mokutil --sb-state                          # "SecureBoot enabled"
bootctl status | grep 'Secure Boot'         # systemd-boot alternative
dmesg | grep -i 'secure boot'               # kernel acknowledgement

# See the cert databases
mokutil --db                                    # authorized certs
mokutil --dbx | head                            # blacklisted (revoked bootkits)
openssl x509 -in <(mokutil --export-kek) -text  # examine a KEK cert
```

### The shim: bridging Microsoft's signing to Linux

Microsoft signs the **shim** bootloader (a small EFI binary maintained by the Linux community). The shim's sole purpose is to add a second, Linux-specific key database — **MOK** (Machine Owner Keys) — and then hand off to GRUB or directly to the kernel.

```bash
# MOK management (for locally-signed kernels or DKMS modules)
mokutil --list-enrolled    # MOK database contents
mokutil --import mykey.der # add a key (requires reboot + UEFI confirmation)
mokutil --disable-validation  # disable signature checking (dangerous)
```

Why does this matter? DKMS rebuilds kernel modules (e.g., NVIDIA, VirtualBox). Without Secure Boot signatures, rebuilt modules can't load. The shim+MOK mechanism lets you sign DKMS modules with your own key and trust that key via MOK.

### Module signing (`CONFIG_MODULE_SIG`)

The kernel refuses to load unsigned modules when Secure Boot is active (and typically always when `CONFIG_MODULE_SIG_FORCE=y`):

```bash
# Check module signature enforcement
cat /proc/sys/kernel/modules_disabled        # 1 = no new modules at all
cat /sys/module/*/signature                  # signature info per module (if available)

# Kernel module signing infrastructure
ls /lib/modules/$(uname -r)/build/certs/     # signing_key.pem, x509.genkey
modinfo usb_storage | grep sig_              # signature metadata
# sig_id:        PKCS#7
# signer:        Build time autogenerated kernel key
# sig_key:       4E:3C:...
# sig_hashalgo:  sha512
# signature:     ... (ASN.1 blob) ...

# Show trusted keys ring
cat /proc/keys | grep -i builtin_trusted     # kernel's keyring
keyctl list %:.builtin_trusted_keys          # same, via keyctl
```

One level deeper: the kernel can require modules to be signed *in a specific keyring only* — `CONFIG_MODULE_SIG_KEY` specifies the key; `CONFIG_MODULE_SIG_ALL` signs all modules at build time.

## The TPM: tamper-proof measurement

The Trusted Platform Module (TPM 2.0) is a separate chip (or firmware implementation — fTPM on AMD, PTT on Intel) that provides:

1. **PCRs** (Platform Configuration Registers): 24+ register slots that can only be *extended* (hashed into), never overwritten or decremented
2. **Sealed storage**: encrypt data that can only be decrypted if the PCRs match a specific value
3. **Attestation**: sign a quote of current PCR values, proving to a remote party what software ran

```text
PCR extension formula:
    new_PCR_value = hash(old_PCR_value || new_measurement)

This is one-way: you can't "un-extend" PCRs.
You can only verify by replaying the expected sequence and comparing.
```

The boot process extends PCRs at every stage:

| PCR | What's measured | Typical contents |
|---|---|---|
| 0 | Platform firmware (BIOS/UEFI) binary | Hash of firmware image |
| 1 | Platform configuration (CPU microcode, setup) | Hash of firmware settings |
| 2 | Option ROMs (PCIe cards) | Hashes of expansion card firmware |
| 3 | Option ROM configuration | Hash of card configuration |
| 4 | Boot manager code (shim) | Hash of shim binary + MOK |
| 5 | Boot manager configuration (GRUB config) | Hash of `grub.cfg` |
| 6 | Power / platform state events | Sleep/wake transitions |
| 7 | Secure Boot state | Whether SB was on, which keys used |
| 8 | Kernel command line | Hash of `/proc/cmdline` |
| 9 | Kernel image, initramfs | Hashes of kernel + grub-loaded files |
| 10 | IMA runtime measurements | Log of every executed binary |
| 14 | shim-specific policy | MOK, SB certificates |

The **Event Log** (`/sys/kernel/security/tpm0/binary_bios_measurements`) records *what* was extended into each PCR. Combined with PCR values, you can **replay** the log to verify integrity:

```bash
# TPM tools
tpm2_pcrread                         # read all PCR values
tpm2_getrandom 32                    # hardware random numbers
tpm2_getcap properties-fixed         # TPM capabilities
tpm2_getcap pcrs                     # which PCRs exist, what banks (SHA-1, SHA-256)

# Event log (binary, then decoded)
cat /sys/kernel/security/tpm0/binary_bios_measurements > /tmp/bios_log
tpm2_eventlog /tmp/bios_log          # human-readable
```

### Sealing: data locked to a boot state

The TPM can **seal** a secret (e.g., disk encryption key) to a specific set of PCR values. If the PCRs don't match (because someone tampered with the boot chain), the TPM refuses to unseal:

```bash
# Create a sealed object that only unseals if PCR 0-7 match expected values
tpm2_createprimary -C o -c primary.ctx
tpm2_create -C primary.ctx -u obj.pub -r obj.priv \
    -i secret.bin -p "pcr:sha256:0,1,2,3,4,5,7"
tpm2_load -C primary.ctx -u obj.pub -r obj.priv -c obj.ctx
tpm2_unseal -c obj.ctx -p "pcr:sha256:0,1,2,3,4,5,7"  # fails if PCRs changed
```

This is the mechanism behind **systemd-cryptenroll + TPM2**: the LUKS2 disk encryption key is sealed to PCR 7 (Secure Boot state). If someone boots a modified kernel or disables Secure Boot, the PCR changes and the TPM won't release the key — the system can't boot without the recovery passphrase.

```bash
# Bind LUKS to TPM (irreversible — make sure you have a backup passphrase!)
systemd-cryptenroll --tpm2-device=auto --tpm2-pcrs=7 /dev/sda3
```

## IMA: Integrity Measurement Architecture

IMA (`CONFIG_IMA`, documented in `Documentation/security/IMA-tpm.rst`) is the kernel subsystem that extends the TPM with runtime measurements. Every file opened for execution (or read, depending on policy) is hashed and extended into PCR 10:

```bash
# IMA status
cat /sys/kernel/security/ima/policy         # current IMA policy
cat /sys/kernel/security/ima/ascii_runtime_measurements  # measurement log

# Example entries:
# 10 sha256:abcd1234... ima-ng sha256:ef567890... /usr/bin/bash
#  │  │                │      │                  └── file path
#  │  │                │      └── file content hash
#  │  │                └── template name ("ima-ng" = next-gen)
#  │  └── PCR 10 value after extension
#  └── PCR number
```

IMA policies control *what* to measure:

```bash
# Default policy (built into kernel or loaded via ima_policy= kernel param):
# measure func=FILE_CHECK                         ← hash every opened file
# appraise func=FILE_MMAP mask=MAY_EXEC          ← verify signature before exec
```

Two IMA modes:

| Mode | What it does |
|---|---|
| **measure** | Just log the hash to PCR 10 (for remote attestation) |
| **appraise** | Verify the file's IMA signature before allowing access — if the signature doesn't match or is missing, access is denied |

```bash
# Enable IMA appraisal (must be on kernel command line, or built-in)
# Kernel params: ima_policy=tcb ima_appraise=enforce

# Check per-file IMA appraisal status:
getfattr -m security.ima /usr/bin/ls
# security.ima: 0s...  (binary: struct ima_template_desc + signature)
```

IMA integrates with **EVM** (Extended Verification Module) to protect file metadata (permissions, owner, ACLs, extended attributes) from offline tampering. EVM computes an HMAC over file metadata using a key sealed in the TPM:

```bash
# EVM status
cat /sys/kernel/security/evm             # current EVM status

# EVM-protected file (offline modification of owner/mode is detected):
getfattr -m security.evm /etc/shadow
```

Together, IMA+EVM form **integrity protection** for immutable infrastructure: every file's content *and* metadata are cryptographically verified against a TPM-anchored chain of trust.

## Measured Boot vs Secure Boot

| | Secure Boot | Measured Boot |
|---|---|---|
| **Goal** | Prevent unauthorized code from running | Prove what code ran |
| **Mechanism** | Signature verification → refuse to execute | Hash → extend PCR → attestation |
| **Enforcement** | At the machine (the machine refuses) | Remote (a server checks PCR quotes) |
| **TPM required?** | No (UEFI variable-based) | Yes |
| **Key use case** | Block bootkits on laptops | Prove VMs are unmodified in cloud |

Both work together: Secure Boot verifies and blocks; measured boot records and proves. A modern attested deployment (e.g., Kubernetes with confidential containers) uses both.

## Confidential computing: TEEs

Beyond measurement and attestation, modern CPUs offer **hardware-isolated execution environments** where neither the host kernel, hypervisor, nor cloud operator can read the workload's memory:

| Technology | Vendor | Mechanism |
|---|---|---|
| **Intel SGX** | Intel | Enclaves in user space, encrypted memory regions, remote attestation |
| **Intel TDX** | Intel | Full VM confidentiality, encrypted per-VM memory, attestation via TDREPORT |
| **AMD SEV** | AMD | Encrypted VM (SEV), encrypted registers (SEV-ES), integrity protection (SEV-SNP) |
| **ARM CCA** | ARM | Realm VMs isolated from host; Granule Protection Table for memory |
| **pKVM** | Android | Protected KVM: small trusted hypervisor runs in EL2 |

These technologies rely on the same TPM-style verification patterns: (1) measure the TEE firmware/measurer, (2) attest to a remote verifier, (3) only then provision secrets.

```bash
# AMD SEV detection on a cloud VM
dmesg | grep -i sev
cat /sys/module/kvm_amd/parameters/sev          # SEV status

# Intel TDX detection
dmesg | grep -i tdx
cat /sys/module/kvm_intel/parameters/tdx        # TDX available
```

## The LUKS2 + TPM2 stack in practice

Modern Linux distributions increasingly use TPM-bound disk encryption:

```bash
# Enroll TPM2 with systemd 248+
# This seals a LUKS key to PCR 7 (Secure Boot state)
systemd-cryptenroll --tpm2-device=auto --tpm2-pcrs=7 /dev/nvme0n1p2

# List enrolled methods (password, TPM2, FIDO2, PKCS#11)
systemd-cryptenroll --list /dev/nvme0n1p2

# Verify the TPM can unseal
systemd-cryptsetup attach mydata /dev/nvme0n1p2 \
    - tpm2-device=auto

# On next boot: no password prompt (if PCR 7 matches)
# If Secure Boot is disabled or shim changes → falls back to passphrase
```

The sealed key is stored in the LUKS2 header as a JSON token. The TPM's private key never leaves the chip — only the symmetric disk key (unsealed inside the TPM's shielded location) is released.

## Container integrity: IMA + container runtimes

Containers change the game: the kernel is shared, but container images are independent of the host's IMA policy. Two approaches:

1. **Host-side IMA**: measure every binary executed on the host (including inside containers). Container A's `/usr/bin/python` and Container B's `python` produce different hashes (different filesystem layers).
2. **Image signing**: container registries sign images (cosign, Notary), the container runtime verifies the signature at pull time, but no runtime measurement.

Combining both: IMA measures what runs, image signing verifies what was pulled, and TPM attestation proves the whole chain to a remote verifier. This is how confidential container platforms (e.g., Kata Confidential Containers, CoCo) work.

```bash
# See IMA measurements from containers
cat /sys/kernel/security/ima/ascii_runtime_measurements | \
    grep -E 'docker|containerd|/run/containerd'

# Container runtime signature verification with cosign
cosign verify --key cosign.pub myregistry/myimage:latest
```

## Try it yourself

```bash
# Full Secure Boot status
mokutil --sb-state
bootctl status 2>/dev/null || true

# Explore TPM
sudo tpm2_pcrread                        # all PCRs
sudo tpm2_getcap properties-fixed        # TPM capabilities

# Check IMA
dmesg | grep -i ima                       # IMA init messages
ls /sys/kernel/security/ima/             # IMA sysfs
sudo cat /sys/kernel/security/ima/ascii_runtime_measurements | tail -5

# Check EVM
cat /sys/kernel/security/evm              # "0" = disabled, others = enumerated

# Module trust
cat /proc/keys | grep builtin_trusted
cat /proc/sys/kernel/modules_disabled

# LUKS + TPM (if using systemd 248+)
sudo systemd-cryptenroll /dev/sdX --tpm2-device=list  # list available TPMs (doesn't enroll)

# Kernel lockdown status
cat /sys/kernel/security/lockdown
# [none] integrity confidentiality  ← if Secure Boot, should be "integrity"
```

## Check your understanding

1. Secure Boot verifies the bootloader's signature and blocks unsigned code. What prevents someone from replacing the Secure Boot database (db) with their own?
2. A PCR is extended 15 times during boot. How can you verify the final value is correct if you can't reverse the extensions?
3. IMA measures every executed binary. A container image was signed at build time but the signature isn't checked at runtime. What is IMA actually verifying?
4. A TPM unseal operation fails even though Secure Boot is still on and the kernel hasn't changed. What common event could have changed the PCR?
5. LUKS2 with TPM-autounlock boots without a password — so what protects the disk if the laptop is stolen?

*(Answers: the PK (Platform Key) signs the KEK, which signs db — to modify db, you need access to a KEK private key or physical UEFI menu access (the user is physically present, entering the UEFI setup); you replay the event log — starting from the initial PCR value (all zeros), you hash each event from the log in order, applying the same extend operation, and compare the result to the final PCR — if they match, the event log is authentic and the sequence hasn't been tampered with; IMA verifies that the binary running right now matches the file on disk — it catches runtime tampering (e.g., a root exploit replacing /usr/bin/sshd) but does not verify the binary's provenance; a BIOS update, a kernel command line change (added or removed a parameter), a GRUB configuration edit, inserting a USB device with a bootable option ROM, or a BIOS setting change (disabling/enabling Intel AMT) — PCRs 0, 1, 4, 5, and 8 are especially sensitive to "minor" changes; physical possession means the attacker can attempt to disable Secure Boot via the UEFI menu — but that changes PCR 7, and the TPM won't unseal the key with the modified PCR set, forcing the attacker to guess the LUKS passphrase, which is the fallback authentication factor.)*
